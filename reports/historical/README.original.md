# Автоматизация генерации признаков в рекомендательных системах

Учебный проект: можно ли заменить ручной подбор признаков (например, окно «7 дней») автоматическим перебором, 
который не проиграет бустингу на ручных признаках.

**Данные:** [Yambda-50M](https://huggingface.co/datasets/yandex/yambda) (Яндекс.Музыка: прослушивания и лайки).  
**Модели:** LightGBM (классификатор и LambdaRank).  
**Метрики:** NDCG@10 и Recall@10 внутри каждого пользователя, AUC. Разницы между моделями проверяются парным bootstrap по пользователям.

## Коротко о результате

1. Модели с признаками заметно лучше случайного порядка и популярности: на test NDCG@10 около 0,08 против 0,0575.
2. **Автоматический генератор (151 признак) не отличим от ручного набора (37 признаков) в пределах шума.** Все интервалы bootstrap для классификаторов включают ноль.
3. Автоматика нашла то, что человек пропустил: самым важным признаком оказалась конверсия юзера в окне **180 дней** (`u_cr_180d`), а в ручном наборе окон длиннее 30 дней не было. Из 37 лучших автоматических признаков 21 использует окно от 60 дней или «всё время».
4. Отбор 37 лучших признаков по важности **не обыграл** ручные 37 при равном бюджете признаков.
5. В ранкере `auto-all` значимо лучше `RANK manual`, но сам `RANK manual` хуже классификатора на тех же признаках. Относительно лучшей ручной модели выигрыша нет.

Чего мы **не** показали: что автоматика превосходит хорошо затюненный ручной бустинг. Подробнее в разделе «Ограничения».

## Постановка

- Строка = прослушивание `(uid, item_id, timestamp)`. `label = 1`, если пользователь лайкнул трек в течение часа после начала прослушивания (около 1% позитивов).
- Подвыборка: 5000 случайных пользователей со всей их историей.
- Сплит по времени: train, затем val (14 дней), затем test (14 дней). Train собирается из 4 недельных срезов перед val.
- **Без утечек:** признаки считаются только по событиям строго до среза, в коде есть `assert`.
- Из кандидатов убраны пары, которые пользователь уже лайкал до среза: новым лайком они стать не могут. Без этого фильтра метрики завышались (AUC около 0,87 из-за артефакта в метке).

## Признаки

**Ручные (37 штук):** user, item, user×item. Окна 1, 7, 30 дней и «всё время». Счётчики прослушиваний и лайков, конверсия `лайки/(прослушивания+1)`, средняя доля дослушивания.  
**+ artist/album (61 штука):** добавлены user×artist и user×album.

**Автоматические (151 штука):** шаблон `сущность × событие × окно`. Сущности: `u`, `i`, `ui`, `uar`, `ual`. Окна: 1, 3, 7, 14, 21, 30, 60, 90, 180 дней и всё время. Генератор: `src/auto_features.py`. 
Отбор: топ-37 по gain-важности (в том числе с отсевом почти дублирующих признаков по корреляции рангов).

### Значимость различий (парный bootstrap по пользователям, 100 повторов)

Разница NDCG@10 на test, 95% интервал. Значимой считается разница, чей интервал целиком по одну сторону от нуля.

| Сравнение | Разница | Интервал | Значима? |
|---|---|---|---|
| CLF manual + artist/album − CLF manual | +0,0027 | [−0,0047, +0,0089] | нет |
| CLF auto-all − CLF manual | +0,0020 | [−0,0052, +0,0090] | нет |
| CLF auto-топ-37 − CLF manual | −0,0016 | [−0,0088, +0,0045] | нет |
| CLF auto-топ-37 (корр < 0,99) − CLF manual | −0,0044 | [−0,0122, +0,0029] | нет |
| RANK auto-all − RANK manual | +0,0109 | [+0,0032, +0,0183] | **да**, но см. ниже |
| RANK auto-топ-37 − RANK manual | −0,0018 | [−0,0092, +0,0054] | нет |
| CLF manual − RANK manual | +0,0108 | [+0,0045, +0,0180] | да |

`RANK auto-all` значимо лучше `RANK manual`, но `CLF manual` лучше `RANK manual` на ту же величину, так что относительно лучшей ручной модели (классификатора) выигрыша нет.

## Ограничения

- Шум: интервалы bootstrap шириной около ±0,007 по NDCG@10. Различия меньше этого порога не подтверждены.
- Один сид сэмплирования пользователей (`seed=42`) и одна выборка из 5000 пользователей.
- Гиперпараметры бустинга и ранкера не тюнились (Optuna не запускался), поэтому «хорошо затюненный бустинг» пока не побеждён и не проверен.
- Test просматривался многократно при сравнении вариантов. Вариант для финального вывода выбирался по val, но отдельного «чистого» test нет.
- Кандидаты это только уже прослушанные пользователем треки, а не весь каталог, поэтому задача ближе к реранжированию.
- Метка («лайк в течение часа») условна; горизонт 1 час не подбирался.
- Масштабируемость: подход проверен на подвыборке в 5000 пользователей; на миллиардах взаимодействий он не проверялся.

## Как запустить

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
# macOS: для LightGBM нужен OpenMP
brew install libomp
```

Минимальный пример:

```python
from src.data import *
from src.features import *
from src.auto_features import build_train_auto, build_auto
from src.models import fit_eval, feature_columns

listens, likes = load_yambda("listens.parquet"), load_yambda("likes.parquet")
L, K = sample_users(listens, likes, n_users=5000, seed=42)
L = make_labels(L, K)
maps = {"artist_id": load_mapping("artist_item_mapping.parquet"),
        "album_id":  load_mapping("album_item_mapping.parquet")}
L, K = add_groups(L, K, maps)
t_val, t_test, t_end = time_split(L)

def ev(a, b, c):
    X = build_auto(L, K, window(L, a, b), c, maps)
    return X[X.ui_likes_all == 0]                 # тот же фильтр, что и в train

Xtr = build_train_auto(L, K, t_val, maps)
Xva, Xte = ev(t_val, t_test, t_val), ev(t_test, t_end + 1, t_test)

feats = [c for c in Xtr.columns
         if c not in ("uid", "item_id", "label", "artist_id", "album_id")
         and not c.startswith(("ui_likes_", "ui_cr_"))]
fit_eval("auto: все признаки", feats, Xtr, Xva, Xte)
```

## Что дальше

- Bootstrap относительно лучшей ручной модели (`CLF manual`) для ранкера.
- Optuna для ручной и автоматической моделей одинаковым бюджетом.
- Несколько сидов выборки пользователей и больше пользователей, чтобы сузить интервалы.
- Другие агрегаты, не только счётчики по окнам (например, давность последнего события, затухание).
