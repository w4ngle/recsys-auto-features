# Методология

[← О проекте](../README.md) · [Результаты](results.md) · [Воспроизведение](reproduction.md)

## Исследовательский вопрос

Я сравниваю ручное проектирование признаков и генерацию агрегатов по шаблону. Основная гипотеза: расширение пространства временных окон может дать полезные признаки, которые не были включены в ручной набор. Эксперимент проверяет качество ранжирования, но не измеряет экономию времени разработки или эффект на продуктовые показатели.

## Данные и целевая переменная

Источник — [Yambda](https://huggingface.co/datasets/yandex/yambda), вариант `flat/50m`. Используются прослушивания, лайки и соответствия треков артистам/альбомам. Из пользователей с прослушиваниями случайно выбираются 5000 (`seed=42`), затем сохраняется вся их история.

Для каждой пары `uid, item_id` определяется время первого лайка. Прослушивание получает `label=1`, если этот лайк произошёл от 0 до 3600 секунд после начала события включительно. Остальные события получают `label=0`.

Пары, лайкнутые до момента среза, исключаются из кандидатов. Повторные прослушивания одной пары остаются отдельными строками. Поэтому NDCG/Recall описывают ранжирование событий и не равнозначны оценке списка уникальных треков.

## Временной протокол

Train состоит из четырёх недельных интервалов перед val. Val — следующие 14 дней, test — последние 14 дней относительно максимального времени прослушивания в подвыборке. Признаки для каждого интервала используют историю строго до его начального среза.

Опубликованный контрольный запуск использует ранее сохранённые таблицы. Они не содержат timestamp/cutoff, поэтому по ним нельзя независимо проверить временную корректность происхождения всех признаков и меток.

В текущем коде пересборки я исключаю последний час каждого обучающего окна, val и test. Это оставляет время наблюдения для часовой метки и исключает использование событий следующей части для завершения предыдущей. Дополнительно при полной пересборке нужно подтвердить полноту likes до выбранного конца наблюдений listens.

**Статус:** зазоры реализованы и проверены на синтетических примерах; полный эксперимент на новых таблицах не выполнен. Опубликованные метрики относятся к предыдущему протоколу.

## Признаки

| Семейство | Сущности | Окна | Используемых признаков |
|---|---|---|---:|
| Ручное основное | пользователь, трек, пара | 1, 7, 30 дней, all-time | 37 |
| Ручное расширенное | дополнительно пользователь–артист/альбом | те же | 61 |
| Автоматическое | все пять сущностей | 1, 3, 7, 14, 21, 30, 60, 90, 180 дней, all-time | 151 |

Агрегаты: количество прослушиваний и лайков, отношение `likes / (listens + 1)`, средняя доля прослушивания для пользователя и трека, признак `is_organic`. После фильтра ранее лайкнутых пар `ui_likes_*` равны нулю; в автоматическом наборе также исключаются `ui_cr_*`.

Маппинги артистов и альбомов сведены к одному значению на трек через `drop_duplicates`; неизвестные значения кодируются как `-1`. Это упрощение: многозначные связи и объединение неизвестных сущностей отдельно не исследовались.

Генератор расширяет заданное человеком семейство агрегатов. Он не выполняет произвольный поиск новых формул. Важность gain описывает использование признака моделью и не доказывает причинный вклад. В ручном наборе уже есть all-time, поэтому длинная история не является исключительной особенностью автоматического подхода.

## Модели и выбор настроек

Основной контрольный эксперимент — `LGBMClassifier`. Модель обучается на бинарной метке, вероятности используются как оценки для ранжирования. До 1000 деревьев, early stopping с patience=50 по binary logloss на val; `random_state=42`, четыре потока.

Повторно применяются лучшие параметры из исторического `optuna_results.json`. Этот JSON не содержит полного журнала, seed или бюджета поиска, поэтому не позволяет восстановить исходную процедуру подбора.

Новый `src/tuning.py` задаёт общий протокол: TPE с seed=42, последовательное выполнение, по умолчанию 30 trials на набор, максимизация пользовательского NDCG@10 на val. Пространство одинаково: learning rate, leaves, min child samples, feature/bagging fractions, L1/L2. История сохраняется в SQLite и CSV. Test не передаётся в функцию поиска. Полный поиск по этому протоколу ещё не запускался.

Исторические эксперименты включают LambdaRank, отбор top-37 по gain и отсев по абсолютной корреляции Спирмена. Они сохранены в архивном ноутбуке. Для нового ранкерного эксперимента нужно явно хранить ключ группы `(cutoff, uid)`; в прежних таблицах отдельного snapshot_id нет.

## Оценка и статистическая проверка

NDCG@10 использует бинарную релевантность и логарифмическое дисконтирование позиции. Recall@10 — доля положительных событий пользователя в первых десяти. Метрики усредняются по пользователям с хотя бы одним позитивом. Пользователи без позитивов исключаются из этой оценки, но не из обучения.

Точные ничьи score разрешаются стабильным порядком входных строк; к неравным оценкам шум не добавляется. Это делает метрики воспроизводимыми для фиксированного порядка таблицы, но точные ничьи остаются чувствительными к этому порядку.

Парный bootstrap пересэмплирует пользовательские разности NDCG с возвращением. Контрольный запуск: 2000 повторов, seed=42, 95% percentile-интервал. В JSON раздельно сохранены исходная разность, среднее bootstrap и границы интервала.

Пересечение интервала с нулём означает отсутствие подтверждённого преимущества в данном сравнении. Оно не доказывает эквивалентность или non-inferiority. Интервалы исследовательские; поправка на многократные сравнения не применяется.

## Область применимости

- Один seed и одна пользовательская подвыборка; устойчивость на других выборках не установлена.
- Test просматривался в ходе разработки и не является новым закрытым подтверждающим периодом.
- Кандидаты определены будущими наблюдёнными прослушиваниями; генерация кандидатов из каталога не реализована.
- Доступность `is_organic` для реального будущего кандидата отдельно не подтверждена.
- Эксперимент не измеряет онлайн-эффект, задержку сервиса или масштабирование на весь поток событий.
